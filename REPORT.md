# Звіт до лабораторної роботи №3

## 1. Тема, номер і варіант

- **Тема:** Спадкування, інтерфейси й поліморфізм у Java-проєкті
- **Номер роботи:** 3
- **Варіант:** 17 — Спортивна ліга
- **ОС:** Windows 11
- **Мова:** Java 21
- **Система збірки:** Maven

## 2. Мета роботи

Класову модель спортивної ліги розширено спільним абстрактним типом
`Match`, двома підтипами, enum категорії та поліморфним нарахуванням
очок. Попередні CSV, статистика голів, відвідуваність і тести збережено.

## 3. Стан до і після роботи

У лабораторній роботі №2 кожен запис створювався одним конкретним класом
`Match`. У цій роботі спільні поля та валідацію винесено до абстрактного
базового типу, а відмінну поведінку реалізовано у `LeagueMatch` і
`PlayoffMatch`. `CsvProcessor` працює зі списком `Match` і не визначає
підтип через `if` або `switch`.

## 4. Базовий тип

`Match` містить команди, рахунок, відвідуваність і `MatchKind`. Поля є
`private final`, а перевірка порожніх назв, від'ємних чисел і null-категорії
виконується під час створення. Абстрактні методи `homePoints()` та
`awayPoints()` задають спільний поліморфний контракт.

Абстрактний клас обрано тому, що обидва підтипи мають однаковий стан і
спільні інваріанти, але різні правила нарахування очок.

## 5. Підтипи

`LeagueMatch` реалізує класичну систему регулярного чемпіонату:
перемога — 3 очки, нічия — 1, поразка — 0.

`PlayoffMatch` реалізує правила плей-оф: перемога — 3 очки, поразка —
0, нічия — 0, оскільки переможець плей-оф визначається додатково.

## 6. Enum

`MatchKind` має значення `LEAGUE` і `PLAYOFF`, а також україномовну
назву категорії. П'ятипольовий старий CSV автоматично вважається
ліговим. Шосте поле може явно містити `LEAGUE` або `PLAYOFF`.

## 7. equals і hashCode

Рівними вважаються записи одного підтипу з однаковими командами,
рахунком і відвідуваністю. Клас підтипу враховується, тому однакові
за полями ліговий матч і матч плей-оф не змішуються. Узгоджені
`equals` і `hashCode` перевірено додаванням дубліката до `HashSet`.

## 8. Поліморфізм

У `CsvProcessor` використовується `List<Match>`. Для кожного елемента
викликаються `homePoints()` та `awayPoints()` через тип `Match`, а Java
автоматично обирає реалізацію відповідного підтипу. Центрального
розгалуження за категорією немає.

## 9. Тестування

Збережено попередні тести CSV і генератора звіту. Додано перевірки:

- створення обох підтипів через `fromCsv`;
- значень `MatchKind`;
- різної поведінки нарахування очок;
- нульових очок для нічиєї у плей-оф;
- рівності та дублювання в `HashSet`;
- валідації спільного базового типу.

Результат `mvnw.cmd -B clean verify`: **20 тестів пройшли**,
SpotBugs не знайшов помилок.

## 10. Інфраструктура

Основні команди:

```powershell
.\mvnw.cmd -B test
.\mvnw.cmd -B clean verify
.\mvnw.cmd -B package
java -jar target\cppt-labs.jar --input data\input.csv --output out\report.txt
```

Проєкт використовує JUnit 5, SpotBugs, Maven Shade Plugin і GitHub Actions.
CI запускає перевірку на Ubuntu, Windows і macOS та публікує JAR як artifact.

## 12. Порівняння поведінки

Для старого `data/input.csv` усі вісім коректних рядків залишаються
ліговими матчами. Показники до і після перебудови однакові:

```text
Коректних записів: 8
Середня кількість голів: 2.63
Найбільша відвідуваність: 12500
Сумарна відвідуваність: 64000
```

Додатково нова модель обчислює:

```text
Сумарна кількість очок: 22
```

## 14. Відповіді на контрольні питання

1. **Навіщо потрібен базовий тип?**  
   Він зберігає спільний стан і правила, щоб не дублювати їх у підтипах.
2. **Чим відрізняються підтипи?**  
   Вони мають спільні поля, але різні реалізації нарахування очок.
3. **Що дає `abstract`?**  
   Забороняє створення неповного `Match` і зобов'язує підтипи реалізувати контракт.
4. **Для чого `@Override`?**  
   Позначає перевизначення методу базового типу й допомагає компілятору перевірити його.
5. **Навіщо enum?**  
   Він обмежує категорію матчу фіксованим набором значень.
6. **Що таке поліморфізм?**  
   Виклик через `Match` виконує реалізацію фактичного підтипу.
7. **Чому не потрібен `instanceof`?**  
   Відмінність поведінки вже інкапсульована у перевизначених методах.
8. **Для чого `equals`?**  
   Для логічного порівняння матчів, а не лише посилань.
9. **Чому `hashCode` має відповідати `equals`?**  
   Так колекції на основі хешування коректно знаходять дублікати.
10. **Що перевіряє `HashSet`?**  
    Що два рівні матчі зберігаються лише один раз.
11. **Як збережено сумісність CSV?**  
    Старий формат із п'ятьма полями залишено, а категорію додано необов'язковим шостим полем.
12. **Чому валідація в базовому типі?**  
    Вона єдина для всіх підтипів і не дублюється.
13. **Що залишилося від попередньої роботи?**  
    Формат, статистика голів, відвідуваність, помилки, JUnit і Maven-інфраструктура.
14. **Чому обрано спадкування?**  
    Підтипи є різновидами матчу та мають однаковий спільний стан.
15. **Як перевірено результат?**  
    Через JUnit, SpotBugs, executable JAR і порівняння контрольного звіту.
